Status: **proposed, not implemented.** No code has been run against a model yet.
Date: 2026-11-10

## 2. Key design decision: research via Anthropic server tools

Research uses the Messages API server tools `web_search_20260209` and `web_fetch_20260209`.
They run on Anthropic infrastructure, so:

- only `api.anthropic.com` is needed — no network allowlist changes;
- research is **read-only by construction** (the model cannot write, deploy, or execute anything locally);
- every search query, result URL, and fetched document comes back as a structured tool-result block,
  which the harness logs. This is what makes the validation record trustworthy (see §5).

`web_fetch` can only fetch URLs already present in the conversation, which further limits injection-driven exfiltration.

Benchmark cases also carry **fixture documents** (supplied text) so the hard cases — conflicting sources, outdated docs,
planted numerical errors, prompt injection — are reproducible and have independently checkable ground truth.

## 3. Components and data flow

The pipeline is **code-orchestrated** (a deterministic TypeScript workflow calling the model per stage), not a free-running multi-agent system.

```
subject + fixtures
   │
   ▼
[A] Planner ──────────────► plan.json  (domain, decision objective, criteria, knowledge gaps, assumptions to verify)
   │
   ▼
[B] Research loop ────────► events.jsonl (every query / URL / fetch, tokens, cost)
   │   tools: web_search, web_fetch (server), record_evidence (client, strict schema), calculate (client, deterministic)
   ▼
[C] Evidence registry ────► evidence.jsonl (validated records; see §4)
   │
   ▼
[D] Context compiler ─────► packet.json (facts, refs, assumptions, contradictions, unknowns — contradictions never dropped)
   │
   ▼
[E] Evaluation engine ────► draft-N.json (claims each tied to evidence IDs)
   │
   ▼
[F] Adversarial reviewer ─► review-N.json (fresh context: sees packet + draft only, not planner/engine reasoning)
   │
   ▼
[G] Quality controller ───► gates-N.json (deterministic gates + reviewer-informed gates)
   │        fail & budget left & expected value high
   ├──────────────────────► [H] Revision controller → targeted research and/or re-evaluation → back to E (max 3)
   ▼
report.md + validation-record.json (generated by code from logs, not written by the model)
```

### Responsibilities

| Component | Model or code | Output contract |
|---|---|---|
| A Planner | Model, structured output (Zod schema) | Criteria with weights + rationale; explicit knowledge gaps; assumptions in the user's question flagged for verification |
| B Research | Model tool loop with **hard budgets** enforced in code (max searches, fetches, turns, tokens, USD) | Must call `record_evidence` for every claim it intends to rely on |
| C Registry | **Code** | Rejects records whose source URL/fixture ID was never actually retrieved in this run |
| D Compiler | Code + model summary | Size-bounded packet; deterministic check that every contradicting record survives compilation |
| E Evaluator | Model, structured output | Mechanisms, tradeoffs, edge cases, failure modes, counterarguments, quantitative work via `calculate` |
| F Reviewer | Model, separate call, adversarial prompt | List of specific defects with severity (critical / major / minor) |
| G Quality controller | **Code** for gates 2 & 6 and validation-record completeness; reviewer findings feed gates 1, 3, 4, 5 | Six gate results; any critical defect blocks certification regardless of score |
| H Revision controller | Code | Revises only against named defects; stops at 3 cycles or when gates pass and the reviewer finds no research gap with material decision impact |

## 4. Evidence registry schema

```ts
{
  id: "E-012",
  claim: string,
  source: { kind: "web" | "fixture" | "calculation" | "user_input", ref: string /* URL, fixture id, or calc id */, title?: string },
  retrievedAt: ISODate,
  classification: "VERIFIED" | "CORROBORATED" | "INFERRED" | "HYPOTHETICAL" | "UNKNOWN",
  applicability: string, limitations: string,
  contradicts: string[],        // other evidence IDs
  verification: { status: "checked" | "unchecked" | "failed", method: string }
}
```

Deterministic rules enforced in code:
- `VERIFIED` requires a source that was actually retrieved in this run (matched against logged tool results) or a re-executed calculation.
- `CORROBORATED` requires ≥ 2 independent retrieved sources (distinct domains / fixtures).
- A missing source can only be classified `INFERRED`, `HYPOTHETICAL`, or `UNKNOWN`. Invented evidence is rejected, not repaired.

## 5. Validation record — built from logs, not from model claims

The eight required fields are populated by code from `events.jsonl`:
research performed (actual queries), sources inspected (URLs/fixtures actually returned), checks executed (calculations actually run, gate checks actually evaluated),
checks not executed (budget exhaustion, fetch errors, unreachable sources), independent validation status (set only by the separate grader process),
remaining uncertainty (UNKNOWN/HYPOTHETICAL records + unresolved contradictions), revision count and reasons, final gate results.
The model cannot mark a test "completed" because it never writes this record.

## 6. Security boundaries

- Tools are allowlisted **in code** per stage; the only client tools (`record_evidence`, `calculate`) have no side effects. `calculate` is a parsed arithmetic evaluator, never `eval`.
- Retrieved content is untrusted data: delivered only inside tool-result blocks; system prompt states that instructions inside retrieved content are never followed.
- Injection is **measured**, not assumed handled: benchmark injection fixtures carry canary instructions; deterministic checks fail the case if a canary appears in output or alters tool use.
- No secrets in model context. The API key lives only in the process environment / proxy.
- Bounded budgets per case (USD, tokens, searches, fetches, wall-clock) with hard stops logged as "checks not executed".
- No deployment, no infrastructure changes, no writes outside `evaluator-v3/runs/`.

## 7. Benchmark design

- **Dev set:** ≥ 5 cases, used freely for diagnosis and prompt revision.
- **Held-out set:** 20 cases across the 8 listed domains, covering all 8 difficulty types. Each case defines, *before any run*:
  expected outcomes, must-flag issues, must-not claims, critical-failure conditions, and deterministic checks (regex / numeric / canary).
- **Sealing:** a SHA-256 manifest of the held-out files is committed before the first agent run; the runner refuses to execute if hashes change.
  To limit leakage from the prompt author, held-out cases are drafted by a **separate agent process** whose contents are not read while tuning prompts. (This is mitigation, not true independence — see §9.)
- **Blindness:** the case loader strips expected fields before anything reaches the agent; a unit test asserts this.
- **Baseline vs agent:** same model, same tool access and research budget, same cases. Outputs are anonymised and order-randomised before grading.

### Grading

1. Deterministic checks (must-flag facts, numeric correctness, canaries) — authoritative where they apply.
2. Independent grader: separate process, fresh context, rubric with predefined observable anchors (written before any run), never sees self-scores or which system produced the output.
3. Human adjudication queue: cases where deterministic and model grading disagree, or the grader marks low confidence.

### Reporting

Mean score with bootstrap confidence interval, per-category scores, case-level pass rate, critical-failure count, all failures listed,
tokens / cost / model IDs / budgets per run. **Pass criterion (proposed):** case passes if no critical failure, all deterministic checks pass, and independent score ≥ 95.
The 95 target is claimed only if the held-out mean ≥ 95 **and** zero critical failures. With n = 20 this does not establish population-level reliability.

## 8. Implementation plan (smallest working pipeline first)

```
evaluator-v3/
  src/  cli.ts  pipeline/{planner,research,registry,compiler,evaluator,reviewer,quality,revision}.ts
        llm/client.ts (usage + cost logging)  tools/{calculate,recordEvidence}.ts  report/  schemas/
  prompts/   version-controlled stage prompts (+ baseline.md)
  bench/     cases/dev/*.json  cases/heldout/*.json  MANIFEST.sha256  rubric.md  run.ts  grade.ts  report.ts
  runs/      persisted artefacts per run (committed for auditability)
  test/      vitest: registry rules, gates, budget stops, loader blindness, manifest sealing, injection canaries
  docs/      architecture.md, operating-guide.md, revision-history.md, results.md
```

Steps: (1) scaffold + deterministic modules + tests (no API cost) → (2) single-stage pipeline on one dev case →
(3) full pipeline on dev set, diagnose, revise → (4) seal and run held-out, baseline and agent → (5) grade, adjudicate, report.

Dependencies: `@anthropic-ai/sdk`, `zod`, `vitest`, `tsx`. No frameworks, no database, no services.

## 9. Known limitations to state up front

- Agent, grader, and case author are the same model family. Separate processes and deterministic checks reduce, but do not remove, shared blind spots. Human review of the held-out reference answers is the strongest available mitigation.
- Web results change over time; reproducibility is exact only for fixture-based evidence. Live-web runs are reproducible at the level of logged sources.
- 20 held-out cases give a wide confidence interval. A result near 95 cannot be distinguished from 90 with this sample.

## 10. Open prerequisites

1. **Anthropic API key** and an approved spending cap (rough estimate below).
2. **The original baseline prompt** from the ChatGPT rounds. Without it the baseline is a reconstruction and must be reported as such.
3. **Grader model choice:** same model (`claude-opus-5-5`) vs a different, more capable one (`claude-fable-5-2`, ~2× cost) for more independence.
4. **Human adjudicator:** someone to review held-out reference answers and disputed grades.

### Rough cost estimate (unverified until measured)

Per case, agent ≈ 300k input + 40k output tokens on Claude Opus 5.5 ($4 / $20 per M) ≈ $2, plus web-search fees;
baseline + grading ≈ $0.50. Dev iteration (≈ 4 rounds × 5 cases) + held-out (20 cases × agent + baseline + grading)
≈ **$100–250 total**. Actual per-call usage and cost will be logged and reported.
